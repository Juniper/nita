## ADDED Requirements

### Requirement: Dedicated NITA ingress controller
NITA SHALL deploy a pinned Traefik controller in the `nita` namespace for its
dedicated, non-default IngressClass. The controller SHALL expose HTTPS on host
port 443, retain the `proxy` Deployment and provide an in-pod HTTP listener on
port 8000 without exposing that HTTP port on the host. It SHALL use only the
permissions needed to discover and serve NITA resources and SHALL NOT expose
its administrative API or dashboard publicly.

#### Scenario: Controller isolation
- **GIVEN** NITA and unrelated Ingress resources exist in the cluster
- **WHEN** the controller discovers routes
- **THEN** it serves only resources assigned to the NITA IngressClass

### Requirement: Webapp and Jenkins routing
The controller SHALL route webapp traffic to `webapp:8000` and `/jenkins` traffic
to `jenkins:8080` without stripping Jenkins' context path or rewriting response
bodies. It SHALL preserve the externally relevant host, client address, scheme
and `/jenkins` forwarded prefix without trusting arbitrary client-supplied
forwarding headers. Redirects SHALL preserve the externally visible port.
Requests larger than 20 MiB SHALL be rejected.

#### Scenario: Jenkins deep link
- **WHEN** a client requests `/jenkins/job/example/` over HTTPS
- **THEN** Jenkins receives the original path and the browser can load the
  resulting page and its assets through the proxy

#### Scenario: Slash redirect through a nonstandard port
- **WHEN** a client requests `/jenkins` through an externally forwarded port
- **THEN** any redirect to `/jenkins/` preserves that externally visible port

#### Scenario: Oversized request
- **WHEN** a client sends a request body larger than 20 MiB through the proxy
- **THEN** the proxy rejects it instead of forwarding it as an accepted request

### Requirement: Jenkins session and identity gate
The proxy SHALL consult the webapp forward-auth endpoint before forwarding
Jenkins requests. It SHALL redirect denied browser requests to login with a
safe return path, fail closed when authentication cannot be checked, replace
client-supplied Jenkins identity headers with the authenticated user's identity
and groups, and remove client-supplied `Authorization` before forwarding.

#### Scenario: Anonymous Jenkins request
- **WHEN** a browser without a valid webapp session requests a Jenkins page
- **THEN** it is redirected to login and cannot reach Jenkins

#### Scenario: Spoofed Jenkins identity
- **GIVEN** a valid webapp session for a non-admin user
- **WHEN** the client supplies administrator identity headers on a Jenkins request
- **THEN** Jenkins receives only the identity and groups returned by webapp authentication

#### Scenario: Authentication service unavailable
- **WHEN** the proxy cannot verify a Jenkins request with the webapp
- **THEN** it does not forward the request to Jenkins

### Requirement: Certificate identity
The controller SHALL terminate HTTPS with the configured certificate and key
stored in a Kubernetes TLS Secret. It SHALL present that certificate for
hostname, IP-address and no-SNI connections rather than an autogenerated default.

#### Scenario: Existing certificate after migration
- **GIVEN** an existing NITA installation with a usable proxy certificate
- **WHEN** it is migrated to Traefik
- **THEN** clients receive the same certificate as before migration

### Requirement: Unbuffered long-lived streams
The controller SHALL forward events from `/api/v1/action-history/{id}/stream/`
and `/api/v1/jenkins/jobs/` streams without response buffering or caching.
It SHALL permit at least 1850 seconds of upstream stream inactivity without
closing an otherwise healthy connection.

#### Scenario: Incremental console output
- **WHEN** either stream emits console output
- **THEN** the client receives it within 2 seconds under normal test conditions
  without waiting for the stream to finish

#### Scenario: Long idle interval
- **WHEN** a healthy stream remains idle for 1850 seconds and then emits an event
- **THEN** the connection remains open and the event reaches the client

### Requirement: Safe cutover and recovery
Migration SHALL validate required routing and certificate resources before
replacing the main proxy, wait for controller readiness, and verify the HTTPS
route and certificate. It SHALL retain the previous proxy configuration and
certificate resources until verification succeeds and document rollback.

#### Scenario: Missing existing certificate
- **GIVEN** an existing installation whose certificate and key cannot be read
- **WHEN** an upgrade is attempted
- **THEN** migration fails with an actionable error before replacing the proxy
  and does not generate a different certificate

#### Scenario: New controller fails verification
- **WHEN** the controller fails readiness or HTTPS verification
- **THEN** the failure is reported and the documented rollback can restore the
  previous proxy using retained resources
