## Context

The `proxy` Deployment uses `hostPort: 443` and a downloaded Nginx config to
serve the webapp and Jenkins. The latter runs under `/jenkins` and its port 8080
is restricted by NetworkPolicy. Two API routes stream Jenkins console output;
the existing proxy permits a 20 MiB request body and a 1850-second upstream
read timeout for those routes. Jenkins' proxy route uses a webapp session
forward-auth endpoint and asserts user and group headers. The optional MCP pod
has a separate Nginx sidecar; the webapp repository has a Compose proxy.
CI currently exercises the backend directly, so it does not prove proxy routing
or streaming works.

## Goals / Non-Goals

**Goals:** Move the main entry point to Kubernetes Ingress and replace the MCP
and Compose Nginx proxies without changing client URLs, certificate identity on
upgrade, CLI restart, Jenkins authentication and isolation, or stream behavior.
Support the existing single-node installer and Kind CI.

**Non-Goals:** Install a general-purpose cluster ingress for unrelated workloads,
automate public certificate issuance, change Jenkins' listeners or the existing
MCP client authentication model, or introduce a load-balancer dependency.

## Decisions

- Deploy a pinned, supported Traefik release as the existing `proxy` Deployment
  in the `nita` namespace, with a single replica, `Recreate` strategy and host
  port 443. Preserve its existing pod selector and proxy label, so upgrades
  avoid immutable-selector replacement and Jenkins' existing NetworkPolicy
  continues to allow only the intended proxy. Provide a readiness check that
  does not expose a public dashboard or administrative API. Vendor and review
  the necessary versioned resources rather than downloading a mutable config at
  install time; do not require Helm on the host. Pin versions and inventory
  their provenance.
- Enable the Kubernetes Ingress provider for a dedicated, non-default NITA
  IngressClass and restrict resource watching and RBAC to the minimum needed
  for NITA; explicitly account for any cluster-scoped discovery permissions.
  Do not consume unclassified or other controllers' Ingress resources. Use
  standard Ingress routes where possible; use pinned Traefik-specific resources
  only where necessary for TLS, headers, redirects, or timeouts.
- Route `/jenkins` and `/jenkins/` to `jenkins:8080` without stripping the
  context path; route other paths to `webapp:8000`. Preserve `Host` and the
  forwarded client, scheme and prefix information needed by Jenkins without
  trusting arbitrary client-supplied forwarding headers. Preserve the existing
  slash redirect's external host and port, including through port forwarding.
  Do not rewrite Jenkins response bodies.
- Preserve the webapp session gate described in the existing
  `gate-jenkins-behind-webapp-session` change. Traefik must consult the webapp
  forward-auth endpoint before forwarding Jenkins requests. The webapp
  companion transforms that endpoint to return a safe login redirect for
  denied requests and Jenkins-named identity headers for valid sessions.
  Traefik must relay the redirect, replace client-supplied identity headers
  with the authenticated user and groups, and remove
  client-supplied `Authorization` before forwarding to Jenkins. Fail closed
  when the auth service fails. Verify this against the actual endpoint and
  Jenkins security configuration. There is no Nginx-compatible response mode.
- Terminate TLS in Traefik with the operator's existing certificate and key
  stored in a Kubernetes TLS Secret. Configure certificate selection so both
  hostname and IP access, including clients without SNI, receive the intended
  certificate rather than an autogenerated fallback; verify this with the
  chosen Traefik release. For new installations, retain the existing
  self-signed certificate workflow and `PROXY`/`CERTS` path overrides.
  Document certificate replacement and reload behavior. Restrict Secret access
  and avoid printing private key material.
- Preserve the 20 MiB request limit and the in-pod HTTP port 8000 routing
  contract without exposing that port on the host. Do not enable response
  buffering or caching for the two SSE routes. Configure upstream and entry
  point timeouts to allow at least 1850 seconds of idle stream time; verify
  actual behavior rather than assuming equivalent timeout semantics. Coordinate
  with the webapp change's local request-only limiter and identity guard; the
  limiter must cover all routes without buffering streaming responses.
- Keep `deployment/proxy` as the CLI restart target. Update installer and
  `apply-k8s.sh` preflight checks to require the new TLS/configuration resources
  and report missing prerequisites. Update Jenkins NetworkPolicy only if
  necessary, and never broaden access to port 8080 beyond the existing intended
  sources. CI must actually apply the policy when testing this behavior.
- Replace the MCP sidecar in place with a separately configured Traefik
  instance, keeping the backend on `127.0.0.1:8091` and host port 8090. Use a
  file-backed dynamic configuration in a Kubernetes Secret to inject the same
  internal bearer token as the backend's `.tokens` file; never expose it through
  a ConfigMap, logs, responses, or the public API. Override a client-supplied
  Authorization header, preserve `/mcp` to `/mcp/` normalization, relevant
  request headers, streaming, and the existing 3600-second timeout. Validate
  token rotation and failure handling so proxy and backend cannot silently
  diverge. The existing unauthenticated external HTTP interface is retained
  only as the documented lab/demo behavior, not represented as secure access.
- The companion `nita-webapp` change replaces its Compose proxy with Traefik
  using explicit file configuration rather than access to the Docker socket.
  Keep the existing external network, port, certificates and Jenkins resolution
  assumptions; verify routing, auth, limits and streaming independently.
- Test the real HTTPS entry point, including routing and Jenkins assets,
  forwarded headers, redirects with a nonstandard external port, certificate
  identity, request limits, authentication, and incremental SSE delivery.
  Include a controllable idle-stream test that verifies the full timeout
  threshold, even if it must run separately from the short PR job.

## Risks / Trade-offs

- Host port 443 cannot be bound simultaneously by both proxies. The single-node
  cutover has a short interruption; use `Recreate`, check rollout and report
  failure explicitly.
- Hostless Ingress and certificate fallback behavior depend on Traefik
  configuration. Verify hostname, IP and no-SNI cases against the pinned
  release; do not rely on Kubernetes Ingress TLS declarations alone to select
  the default certificate.
- Controller RBAC, TLS Secret access, and forwarded headers expand the security
  surface. Restrict scope and verify policy enforcement using the supported
  Calico environment as well as Kind where applicable.
- Traefik's auth denial handling, identity header replacement, and stream
  timeouts need end-to-end verification with the current Jenkins security
  changes; a misconfiguration could expose Jenkins or break sessions.
- MCP remains unauthenticated HTTP on the host network for lab/demo clients.
  A proxy replacement does not make that existing trust model safe for
  untrusted networks.
- Compose and Kubernetes span repositories. Coordinate releases and retain
  independent rollback paths for the main proxy, MCP sidecar and Compose.

## Migration Plan

1. Before changing the Deployment, preflight controller resources, port
   ownership, routes, and certificate/key availability. On upgrade, import the
   existing certificate and key from the configured files or existing
   `proxy-cert-cm`; fail with actionable diagnostics if neither is usable.
   Never silently generate a replacement for an existing installation.
2. Create and validate the TLS Secret and controller resources, then replace the
   `proxy` Deployment using its existing selector. Wait for readiness and verify
   HTTPS routes and certificate identity. Preserve the old Nginx configuration
   and certificate resources until the cutover has been verified.
3. If verification fails, reapply the previous proxy Deployment, its
   configuration, and the compatible previous webapp image; wait for readiness
   and verify the old HTTPS route and Jenkins authentication. Document commands
   and prerequisites for rollback and retry; do not remove old resources
   automatically before success.
4. Upgrade the optional MCP sidecar only when MCP is installed. Preserve its
    existing token and backend configuration; verify an actual MCP request,
    rotation and rollback. Do not remove MCP resources for installations that
    declined the optional component.
5. Upgrade Compose separately using the companion webapp change. Preserve the
    certificate/key and existing configuration for rollback.

## Validation

Traefik v3.7.19 and the resources in this change passed isolated Kubernetes
tests for hostname, IP and no-SNI certificates, routing, authentication and
identity-header spoofing. Full-duration 1850-second SSE and 3600-second MCP
idle streams passed with the pinned proxy. The amd64 tests and ARM64 proxy
tests under emulation passed; the gated native ARM64 integration run remains
outstanding.
